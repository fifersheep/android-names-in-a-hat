# Plan — Build the app shell: single activity, navigation, theme and insets

## Intent
This replaces the placeholder `MainActivity` with the 3.0 shell:
- one activity running Navigation 3 with the spec's three typed destinations and its back-stack rules
- list-detail on large windows
- the Top Hat theme (dynamic colour on 12+)
- edge-to-edge insets, predictive back, and the platform splash
- launch routing from the real settings store (NAM-6)

Each destination shows a placeholder backed by a Hilt ViewModel, so NAM-8, NAM-9 and NAM-10 can fill in screens without touching navigation.

## Approach
- **Dependencies** (`gradle/libs.versions.toml`):
  - `material3` pinned to **1.5.0-rc01** outside the BOM. Spec API stability: in 1.4 the expressive theme and motion APIs are internal. The BOM stays 2026.09.00.
  - BOM-managed: `adaptive`, `adaptive-layout`, `adaptive-navigation3` (all 1.3.0).
  - `navigation3-runtime/ui:1.2.1`
  - `lifecycle-viewmodel-navigation3:2.11.0` and `lifecycle-runtime-compose:2.11.0`
  - `hilt-lifecycle-viewmodel-compose:1.4.0`
  - `kotlinx-serialization-core:1.13.0`, plus the `org.jetbrains.kotlin.plugin.serialization` plugin at the Kotlin version, declared root `apply false` like the others (`build.gradle.kts:4-12`)
  - `core-splashscreen:1.2.0`
  - Test dependencies: `kotlin-test`, `kotlinx-coroutines-test`.
- **Keys** (`navigation/AppKey.kt`): `@Serializable sealed interface AppKey : NavKey` with `Lists`, `Draw(listId: Long)` and `EditList(listId: Long?, isNew: Boolean = false, session: Long)`.
  - `isNew` decides rule 2 against rule 3 on Done, and survives process death in the key.
  - `session` is a fresh random id, made by `newList()` and `editList()`, and copied by `listCreated()`. EditList's contentKey is `"EditList:$session"`. Two different Edit list visits never share a ViewModel or saved state, yet `listCreated` keeps the same entry (see Assumptions).
- **Back-stack operations** (`navigation/BackStack.kt`): pure extension functions on `MutableList<NavKey>`, unit-tested.
  - Every operation keeps `Lists` at index 0 and is one or two list writes.
  - The same operations work single-pane and two-pane, because "truncate to Lists, then push" is a no-op truncate when Lists is on top.

  | Operation | Effect |
  |---|---|
  | `launchStack(activeId)` | Builds the starting stack |
  | `openList(id)` | Truncates to `[Lists]`, pushes `Draw(id)` |
  | `newList()` | Truncates to `[Lists]`, pushes `EditList(null)` |
  | `editList(id, fromDraw)` | Pushes, or truncates then pushes |
  | `listCreated(id)` | Replaces the top `EditList(null)` with `EditList(id, isNew = true)` |
  | `doneEditing()` | If the top is new, replaces it with `Draw(id)`; otherwise pops |
  | `back(singlePane): BackResult` | Pops, and reports `LeftList` when a Draw was popped onto Lists in single pane |
  | `listGone(id)` | Removes every entry for that id |

- **Shell** (`navigation/AppNavigation.kt`):
  - `rememberNavBackStack(*start)`.
  - `NavDisplay` with `rememberSaveableStateHolderNavEntryDecorator()` and `rememberViewModelStoreNavEntryDecorator()`. The saveable holder is what keeps in-progress text across process death for every screen.
  - `onBack` calls `back(singlePane)`, and on `LeftList` calls `ShellViewModel.onLeftList()` → `ActiveGroup.close()` (spec Launch: clear only on an explicit phone back-out).
  - Wrapped in `SharedTransitionLayout`, with `sharedTransitionScope = this`, so NAM-8 and NAM-10 can add the morphs.
  - The `EditList` entry uses `contentKey = "EditList:$session"`, so `listCreated` swaps the key without remounting the entry or losing its state. A new visit always gets a new session.
- **List-detail:**
  - Mechanism: `rememberListDetailSceneStrategy(directive = …)`, with `@OptIn(ExperimentalMaterial3AdaptiveApi::class)` accepted in the spec.
  - Directive: `maxHorizontalPartitions = 2` only when `isListDetail(windowSizeClass)`, meaning width ≥ 840 dp **and** height ≥ 480 dp. Otherwise 1, with the spacers at 0. The default ignores height, so a landscape phone would split.
  - Pane metadata:
    - Lists gets `listPane(detailPlaceholder = "Pick a list to draw from")` + `preferredPaneSize(360.dp)`, or 400 dp at ≥ 1600 dp.
    - Draw and EditList get `detailPane()`.
  - Placeholders hide Up when `LocalListDetailSceneScope` is non-null.
  - Back pops one entry: `backNavigationBehavior = BackNavigationBehavior.PopLatest`. The default `PopUntilScaffoldValueChange` would pop EditList and Draw together, but spec `:284` says back from Edit list returns to Draw.
  - Task 7 confirms that `NavDisplay` calls our `onBack` once per back. If it calls it per entry, `back()` stays correct because it pops one entry per call.
- **Launch:**
  - `ShellViewModel` (`@HiltViewModel`) exposes `start: StateFlow<List<AppKey>?>`. It is built from `prefs.activeGroupId.first()`; an `IOException` is logged and gives `[Lists]`.
  - `MainActivity` calls `installSplashScreen()`, then `super.onCreate`, then `enableEdgeToEdge()`, then `setKeepOnScreenCondition { vm.start.value == null }`, then `setContent { NamesTheme { start?.let { AppNavigation(it) } } }`.
  - Routing is optimistic and never queries Room (decision 2026-11-14). After process death, the saved stack wins over `start`.
- **Stale or deleted list:**
  - `DrawViewModel(listId)` (assisted) calls `ActiveGroup.open(listId)` in `init`.
  - Both `DrawViewModel` and `EditListViewModel` expose `status: StateFlow<ListStatus>` (Loading, Present(label) or Gone) from `GroupRepository.observeGroup`. EditList reports Gone only once it has an id. The name `ListStatus` avoids `:shared`'s `draw.DrawState`.
  - Whichever entry is showing reacts to `Gone` the same way: `backStack.listGone(id)` + `ShellViewModel.onListGone(id)`. `ShellViewModel` owns the scope and calls `prefs.clearActiveGroupIf(id)`.
  - This covers a stale id at launch, and a delete from the Lists pane in two-pane mode whether Draw or Edit list is in the detail pane.
- **Theme** (`ui/theme/`):
  - `NamesTheme` = `MaterialExpressiveTheme(colorScheme, MotionScheme.expressive(), typography = NamesTypography)`.
  - `colorScheme` is `dynamicLight/DarkColorScheme` on API 31+. Otherwise it is `lightColorScheme(...)` / `darkColorScheme(...)` with every role from spec Palette. Unlisted roles keep token defaults.
  - `NamesTypography` sets DM Serif Display (`res/font/dm_serif_display.ttf`) on display* and headline*. Shapes are the defaults: `extraLarge` is already 28 dp.
- **Splash and window themes** (`res/values/themes.xml`, plus `values-night`):
  - `Theme.NamesInAHat.Starting` (parent `Theme.SplashScreen`): background `#35319A`, icon `@drawable/ic_launcher_foreground`, post theme `Theme.NamesInAHat`.
  - The icon's art is centred and scaled by about 0.8 to fit the 66 dp safe zone of a 108 dp viewport: it spans about 64×53 and sits off-centre. That makes it fit the splash's 72/108 circle too.
  - `Theme.NamesInAHat` is platform Material NoActionBar, light or dark.
  - No exit animation, because of the API 31–32 system-bar gotcha.
- **DI** (`di/StorageModule.kt`):
  - `@Singleton` `NamesStorage(context)` and `SettingsStorage(context)`. Each must be one per process (NAM-5 and NAM-6 hand-offs).
  - Provides `GroupRepository`, `NameRepository`, `PreferencesRepository`, `ActiveGroup` and `GroupEditor` from them.
- **Placeholders** (`ui/placeholder/`):
  - Each is a `Scaffold` with a `TopAppBar`, using the Scaffold's default insets and `collectAsStateWithLifecycle`. Each has buttons that drive the back-stack operations.
  - Lists shows real groups (tap to open, Edit, Delete) and a "New list" FAB.
  - EditList has a `rememberSaveable` text field. Commit runs `GroupEditor.create` and then `listCreated`.
- **Alternatives considered:**
  - `NavigableListDetailPaneScaffold` (experimental too). Dropped because the spec chose the scene strategy.
  - Keeping the splash up for a DB existence check. Rejected by the user, 2026-11-14.
  - Default contentKey for EditList. Rejected: the remount loses the screen state on create.
  - An in-memory prefs fake. Moot now that NAM-6 has merged.

## Assumptions & open questions
- [answered 2026-11-14] Bind NAM-6's real `SettingsStorage` with no fake. The work waited for NAM-6 (PR #27). Logged in workflow.md.

- [assumed] Pin `material3:1.5.0-rc01` and bump it when 1.5.0 final ships. This follows spec API stability (`3.0-spec.md:470-475`). 1.5.0 final isn't out (research.md, Libraries).
- [assumed] `EditList` gets an extra `isNew: Boolean = false` beyond the spec's `EditList(listId: Long?)`. Rule 2 (Done on a new list → Draw) and rule 3 (Done on an existing list → pop) can't otherwise be told apart after process death, because Lists' overflow can also open `EditList(id)` (`3.0-spec.md:111`). The change is additive, and the spec's key shape stays recognisable.
- [assumed] EditList's contentKey is the key's `session`, not the default (which includes `listId`) and not a fixed class key.
  - **Not the default:** it would remount the entry on `listCreated`, dropping focus and the keyboard after the name is committed (spec Edit list: Next moves on to the add field).
  - **Not a fixed class key:** the critic showed that two-pane "truncate then push" would reuse one visit's ViewModel and text for another list.
  - The EditList ViewModel takes its id from the key on (re)creation, and tracks a created id itself while alive.
  - Task 5 updates `3.0-spec.md:73` to the new key shape, so NAM-8 and NAM-9 see it.
- [assumed] Room's `MultiInstanceInvalidationService` is removed from the merged manifest (`tools:node="remove"`) to meet AC1 literally.
  - It is never started: `DatabaseBuilder.kt:20-26` doesn't call `enableMultiInstanceInvalidation`.
  - A comment says to restore it if that ever changes.
  - Alternative: reword AC1 to "no app-declared Service". **Flagged at gate 1.**
- [assumed] In two-pane, picking a list or New list replaces the detail instead of pushing, so back from a detail returns to Lists (research D-b; spec rule 5).
- [assumed] "Phone" in the clearing rule means single-pane layout. Back from a two-pane detail doesn't clear the active list; only a delete does (research D-c; `3.0-spec.md:96-99`).
- [assumed] A failed settings read at launch (`IOException`) routes to `[Lists]` and logs. Corruption is already handled by NAM-6 (`SettingsStorage.kt:44-58`; NAM-6 report.md:75).
- [assumed] Icon:

- [assumed] Two-pane insets: each pane's Scaffold applies window insets, so the detail pane may add a start cutout inset it doesn't need. AC4 on the tablet decides whether that needs a fix. If it does, the fix is a deviation inside task 7.
